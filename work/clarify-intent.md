# 澄清意图

把 AI 协作中「不对劲」的瞬间显性化：记下「我以为它知道什么 / 它实际做了什么 / 差在哪」，产出可直接粘回对话的一段话；反复出现的同类偏差沉淀成用户自己的规则。

## 目标

- 每次「不对劲」落成一次显性修订，产出一段可直接粘回对话的提示词，而不是重写整条 prompt。
- 反复出现的同类偏差沉淀成规则；规则归用户所有，换哪个 AI 客户端都带着走。

### 元目标

- 人对 AI 的判断留在自己手里、白箱可查，不交给厂商的黑箱记忆。

## 核心问题

- 三种触发时机是否都成立：开始前声明、过程中卡点、结束后回看。现有流程把 skill 只挂在「过程中」，声明与复盘只是普通命令——开始与结束两个时机要不要升级成流程、升到哪一步未定。
- 沉淀数据落在哪一层：server 侧 SQLite 单库（多客户端共享、结构化查询），还是第二大脑 `data/context/<集>/intention/` 的 Markdown（白箱、可编辑器直接看改、随仓库迁移）。
- 用户愿不愿多花一步（主动召唤、写几行）：主流产品都在消灭这一步，工具成立与否取决于此，不回避、反而把它当筛选器。

## 已决策

- 命名统一为「澄清意图」，不再用「人机协作」这类模糊说法；对外不用「意图」「上下文差」「显性化」当卖点词，只说「你以为它知道的」和「它实际知道的」。
- 一个对象三种状态：intent 的生命周期是 declared → revised → closed；过程中每次偏差是对同一份意图的一次 revision，不是新记录。
- 用户只回答一个问题：「我的意图要不要更新？」不要求先分类这是偏差还是意图。
- 命令行采用 noun-verb 风格，统一前缀 `qtfounder work clarify`（`intent` / `revision` / `rule` 三组），契约见 [clarify-intent-cli.md](./clarify-intent-cli.md)。
- 架构线不变：HTTP API 是唯一真相，CLI 是薄客户端；skill / CLI / 未来的 MCP 适配都只是同一层的调用方。
- 规则由用户点头才落库，工具不自动生成规则文本。
- skill 只在「过程中」挂载（触发 revise）；声明与复盘是冷静动作，用普通命令即可，不包装成仪式。
- 核心指标只有一个：生成的提示词被粘回对话的比例。比例高则工具成立；低则说明「显性化上下文差」没翻译成功，回去改 revise 的引导，不加功能。
- 第一版不做：向量检索（用字符串/关键词打分）、多用户、同步、MCP 适配、自动生成规则文本、被动触发、reopen 语义（先只做「新建」）。

## 待决策

- 开始前的声明与结束时的复盘要不要升级为带引导的流程（现为普通命令），卡在缺一次真实使用的验证。
- 存储落点：SQLite 单库与 `<集>/intention/` 的 Markdown 二选一或分层，卡在「多客户端共享」与「白箱可编辑」何者优先。
- intent / revision / rule 与第二大脑 intention 层的字段是否对齐（同构落盘），未定；skill 第一版的 `deviations.md`、`rules.md` 将来迁成 server 状态时一起定。
