# Agent 协作治理

当前先回答一个问题：写入时的校验值不值得装。答案要从存量里数出来，不靠推演，所以先做巡检，不做闸门。

顺序的理由有三条。巡检不改代码，也不影响现有写法，成本最低。它数出来的量直接决定闸门要不要装、该装在哪一层。反过来先搭闸门再找理由，等于用工具证明工具该存在。

后置的代价是双份的。闸门每晚一天，进库的问题就多一天，而且只能等人读的时候才发现。校验单元每晚一天，规则就多绑在当次对话里一天，对话一结束就蒸发。

## 巡检

把历史写入按今天的规则重判一遍，数出「进库时就有问题、后来靠人改掉」的量。这个数回答的是：没有闸门的时候，漏过去多少。

- 逐次重判存量，按层级与时间两个方向分开数
- 真问题与提及分开计，误报单独一栏
- 抽一批人工复核，确认机器数可信

做完的样子：能一句话说出漏过去的量，以及其中被人工发现的比例；抽检任一条，陌生人当场可判。

## 闸门

在写入那一刻拦下。读路径保持现状——读偏了只是体验差，不污染库。

- 只在写入处校验，先不追加生成端的约束
- 不合规就打回，让写的一方自己改
- 判不准的放行并记下，攒成规则候选

做完的样子：一次不合规的写入当场被挡住，而且不依赖写的人记得去跑检查。

## 校验单元

每条规则要能离开对话独立使用：结构、语义、正反例三样齐备。语义不在工件里，纠正就随对话蒸发。

- 每条规则配一正一反两个例子，例子比说明省力
- 语义写清这一类与相邻那类的界线
- 例子取自真实误判，不编造

做完的样子：没有上下文的执行者读完单元，判断与创始人一致；拿不准的案例能被单元自己解释，不必再回来问。

## 审计报告

监督的对象从「混乱」这个抽象物，换成一条条具体违规。这是它比规则更容易被外人读懂的地方。

- 只说哪条不对、该怎么改，不解释系统结构
- 结论句用日常语言，术语不出现
- 每期只给一处最值得改的，不铺开清单

做完的样子：不写代码的家人读完，能指出哪一条不对，并说出理由。

## 度量

治理有成本，误拦和漏过都要计价，否则约束会一路涨下去。

- 记误拦：好写入被挡下的次数，以及善后花掉的时间
- 记漏过：进库之后才被发现的次数
- 记维护：读、改、迁一条规则要多久

做完的样子：能比较一次误拦与一次漏过的代价，并据此删掉不划算的规则。
