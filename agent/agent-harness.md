# Agent 协作治理

闸门已经装在提交那一刻：只拦这一笔新引入的错误，存量放行，嫌疑与目录级体裁要求归人判。

接下来要回答的是它拦得准不准。答案只能从存量里数：把历史写入按今天的规则重判一遍，看有多少问题当年漏过去，又有多少是机器判错。巡检给闸门一个基线，也给规则一条删改的路。

顺序的理由：巡检不改代码，也不碰现有写法，成本最低；它出的数字决定哪条规则该留、哪条该删。审计报告放最后，等闸门与巡检都跑过一段，它才有东西可写。

## 巡检

把历史写入按今天的规则重判一遍，数出「进库时就有问题、后来靠人改掉」的量。这个数回答的是：没有闸门的时候，漏过去多少。

- 逐次重判存量，按层级与时间两个方向分开数
- 真问题与提及分开计，误报单独一栏
- 抽一批人工复核，确认机器数可信

做完的样子：能一句话说出漏过去的量，以及其中被人工发现的比例；抽检任一条，陌生人当场可判。

## 审计报告

监督的对象从「混乱」这个抽象物，换成一条条具体违规。这是它比规则更容易被外人读懂的地方。

- 只说哪条不对、该怎么改，不解释系统结构
- 结论句用日常语言，术语不出现
- 每期只给一处最值得改的，不铺开清单

做完的样子：不写代码的家人读完，能指出哪一条不对，并说出理由。
