# 迷雾中的司令部：开发路线图

**日期**：2026-10-25

**状态**：主干已定，四项未决

**前置**：《系统契约》《架构设计说明书 v1.1》《验收标准》

本文规定开发顺序、阶段门槛与验收方式。四个里程碑串行推进，每个里程碑只负责消除一条差距；前一个里程碑的验收未通过，不进入下一个。

## 1. 出发点

### 1.1 现有能力

路线图从仓库已有的实现出发，不另起一套。

- 结算逻辑：`combat.dart` 与 `game.dart` 里的机动、攻击范围计算，重构签名后迁入引擎。
- 世界状态：`game.dart` 里的兵力与地形字段，需与结算逻辑拆开。
- 想定数据：帝丘店的三份 JSON（campaign.json、map.json、units.json），含援军波次。
- 相位概念：`game_controller.dart` 的阶段枚举，相位表的替换对象。
- 几何计算：`battlefield.dart`，迁为引擎的六角格辅助，归属需写死。
- 情报界面：intel_view.dart 当前为占位，认知管线落地后才有数据来源。
- 玩法设计：设计稿与验收场景，认知层与敌军决策的设计输入，对应代码为零。
- 测试目录：tests/ 从 M1 起承接确定性测试。

### 1.2 四条差距

| 编号 | 差距 | 现状 | 消除阶段 |
|------|------|------|----------|
| G1 | 引擎没有独立身份 | 结算与界面同包，随机数直接调用，无种子管理 | M1 |
| G2 | 对局不可审计 | 事件与报告不分，无档案，无从比对 | M2 |
| G3 | 认知层为零 | 过滤、延迟、失真、信念、参谋只有设计稿 | M3 |
| G4 | 人机与批量不分 | 单一控制器驱动全部流程，没有人类入口 | M1 相位表，M3 批量，M4 人类入口 |

### 1.3 阶段与周期

周期按单人业余投入估算，每周十到十五小时。

| 阶段 | 目标状态 | 消除 | 周期 |
|------|----------|------|------|
| M1 | 可复算 | G1 | 4–5 周 |
| M2 | 可复盘 | G2 | 3–4 周 |
| M3 | 可对弈 | G3 | 6–8 周 |
| M4 | 可交付 | G4 | 4–6 周 |

贯穿规则：前一阶段的验收未通过，不进入下一阶段；每节的「未达标处理」属于正文，不删不省。

## 2. M1 可复算

**目标**：引擎从界面中拆出，成为不依赖 Flutter 的纯 Dart 包；同一组命令配同一个主种子，双跑零偏离。

**前置**：无。

### 2.1 任务分解

#### 2.1.1 拆包（1 周，消除 G1）

建立 Dart workspace，按三层分包：

```
packages/
  engine/    纯 Dart 包，pubspec 不出现 flutter，CI 检查
  studio/    现有 src/studio 整体迁入，增加 engine 依赖
  tools/     M2 的命令行入口住这里
```

迁移关系：

- `combat.dart` 迁入引擎的战斗结算。
- `game.dart` 拆开：机动与攻击范围进机动结算，兵力与地形进世界状态。
- `battlefield.dart` 的邻居与距离迁入引擎的六角格辅助。
- `game_controller.dart` 的阶段枚举换成引擎的相位表。
- assets/campaigns/diqiudian/ 升格为引擎的想定。

被迁走的模型文件删除，不留兼容层。

#### 2.1.2 四个基础模块（1 周）

- 时钟：回合号只有一个来源，推进由主循环独占。
- 名册：番号注册表，沿用帝丘店现有命名，不另造命名体系。
- 随机数：主种子一次注入，按名字派生子流，未注册的取用点直接抛错，不提供重置。
- 记录：JSONL 追加写入，只提供追加、读取、计数；M1 只开命令卷与事件卷。

#### 2.1.3 内核、世界与最小相位表（1.5 周，消除 G4 的相位部分）

- 内核：`resolve(action, context, rng) → result`，纯函数，随机数只从传入的子流取。
- 世界：`new_game(scenario)` 唯一初始化，`apply(result)` 唯一写入。M1 只支持位置、兵力、地形三项。
- 相位表：五个相位，依次为友方决断、命令下发、机动结算、事件下发、回合归档。友方决断先由固定脚本喂命令，控制器里的阶段分支退役。
- 主循环：在相位之间做校验与登记。

#### 2.1.4 想定 v0（0.5 周）

- 三个 JSON 升格为想定格式 v0，包含地图拓扑、初始部署、主种子。
- 代码里硬编码的地形参数迁入参数表。
- 想定与参数表都写版本指纹。
- 帝丘店作为第一个通过校验的想定。

#### 2.1.5 重演与比对（1 周）

- 命令行工具 `replay` 读档案重演；`diff` 逐事件比对，输出第一处偏离的回合、相位与两侧事件原文。
- M1 的验收由 diff 机械判断，肉眼比对不计入结果。

### 2.2 验收标准

| 编号 | 标准 | 验证方式 |
|------|------|----------|
| A1 | `engine` 包不依赖 Flutter | CI 检查 pubspec |
| A2 | 同种子、同命令流双跑，事件卷逐字节一致 | `diff` 报零偏离 |
| A3 | 更换主种子，`diff` 必现偏离并指出第一处 | `diff` |
| A4 | 帝丘店想定 v0 通过校验，指纹落档 | 命令行 |
| A5 | 现有界面功能不回退 | 人工走一局 |

### 2.3 风险、后置代价与未达标处理

最大的风险是浮点不确定。Dart 的 `double` 跨平台不保证一致，因此 `engine` 包禁用 `double`，数值用整数（米、千分比），并进 lint 检查；这条从第一天执行。

第二个风险是随机数取用点失控。子流未注册即抛错，新增取用点必须显式登记。

后置代价：确定性后补，要重审结算路径、随机数取用点与全部测试夹具，改动范围随开发推进而扩大。

未达标处理：A2、A3 不过即冻结新功能，只做确定性修复；不以临时容忍差异换进度。

## 3. M2 可复盘

**目标**：五卷档案齐备，事件与报告在关卡处分开，一局打完能还原命令、事件、情报、信念与决策，并定位第一处偏离。

**前置**：M1 验收通过。

### 3.1 任务分解

#### 3.1.1 战斗与补给模块化（1.5 周）

- 战斗结算改为 `execute(world, attacker, defender, turn)`，随机数走子流。
- 补给新建。M2 只做补给线连通判断与补给状态事件，复杂规则留到 M4：补给是看不见的系统，先要有可断言的形态。
- 两个模块的数值全部进参数表，清掉残余的裸数值。

#### 3.1.2 相位表补齐（0.5 周）

扩展到十相位，含战斗结算、补给评估与敌方相位占位；相位表指纹落档。

#### 3.1.3 关卡与登记（1 周，G2 的核心）

- 关卡：事件到报告的翻译落在引擎的运行时模块。M3 建指挥部包时迁过去，成为指挥部唯一输入。
- 事件格式以现有电报日志为素材起步，含类型、部队、回合、相位四项，另留一个后果槽位。
- lint 立规：事件类型不得跨运行时边界导出；M3 升格为指挥部源码出现事件类型即编译失败。
- 情报卷从 M2 起记录。

#### 3.1.4 想定文件完整化（1 周）

- 援军波次进格式，胜负条件进格式。改 JSON 即改结局，代码不动。
- 后果槽位先留空，M4 填充，避免届时改档案结构。

#### 3.1.5 命令行入口（1 周）

- 建立开局与推进：new、step。
- 建立查档：report、truth、inspect；inspect 先支持命令卷与事件卷，决策卷到 M3 才有内容。
- 建立校验与比对：validate、diff、replay；diff 支持对比任意两份档案的任意两卷。

### 3.2 验收标准

| 编号 | 标准 | 验证方式 |
|------|------|----------|
| A1 | 帝丘店全流程由脚本命令驱动跑完，五卷齐备并通过校验 | 命令行 |
| A2 | 同种子重跑，`diff` 零偏离，含情报卷 | `diff` |
| A3 | 人为注入一处结算偏移，三分钟内指出第一处偏离的回合与相位 | 注错演练 |
| A4 | 援军波次与胜负条件从想定读取，改 JSON 即改结局 | 改档验证 |
| A5 | 事件格式含后果槽位 | 格式审查 |

### 3.3 风险、后置代价与未达标处理

最大的风险是战斗重构引入行为漂移。现有原型已有隐性平衡，纯函数化时数值容易变，因此迁移前先录一组旧基线（输入命令与战损序列），重构后对基线，漂移要么解释要么修复。

后置代价：档案结构后补要迁移既有对局；事件与报告一旦在上层混用，再分离要改所有读取路径。

未达标处理：A3 演练失败说明 `diff` 粒度不够，先补 `diff` 再继续。

## 4. M3 可对弈

**目标**：认知管线与敌军决策落地，双方在信息不全的条件下完成一局，判断可追溯。

**前置**：M2 验收通过。

### 4.1 任务分解

#### 4.1.1 指挥部包与类型隔离（0.5 周）

- 新建 `packages/command/`，纯 Dart，只依赖引擎公开的报告类型与参数表。
- 关卡的翻译函数从引擎迁入指挥部包。
- lint 升格为硬检查：指挥部源码出现事件类型即编译失败。迷雾从这一刻焊在类型层。

#### 4.1.2 过滤、延迟、失真（1 周）

- 三道处理各自为纯函数，参数进参数表。
- 帝丘店的情报规则作为第一个参数化实例。
- 设计稿里的情报时间线作为手写期望。

#### 4.1.3 研判（1.5 周）

- `assess(turn, reports, beliefs) → beliefs`，纯函数，回合号显式传参。
- 第一版只做位置估计与置信度，不做复杂推断。
- 性质断言先写：同一批情报重算两次，估计跳变有上限。

#### 4.1.4 决断（2–3 周，全路线图最不确定的一段）

- `decide(turn, beliefs, rng) → decision`，候选打分后择一。
- 权重与候选集全进参数表，为 M4 的参数扫描铺路。
- 每次输出由主循环写入决策卷，决断本身保持纯函数。
- 验收用结构断言：置信度低时不大举进攻；打分与最终选择一致。「打得好不好」留给人工对局。

#### 4.1.5 参谋翻译（1 周）

- 两级展开：先把战役级命令展开成部队任务，再逐条做合法性预检。
- 预检失败生成事件回传，不静默丢弃。

#### 4.1.6 双 AI 对弈与参数扫描（0.5 周）

- 主循环的无人值守模式：两侧都由自动决断驱动，与人机对局共用同一张相位表。
- `sweep` 最小版，为 M4 调参积累工具。

### 4.2 验收标准

| 编号 | 标准 | 验证方式 |
|------|------|----------|
| A1 | 指挥部包零事件引用 | CI |
| A2 | 双 AI 对弈跑完帝丘店，五卷齐备 | 批量入口 |
| A3 | 决断的性质断言全部通过 | 测试套件 |
| A4 | 同种子批量双跑，`diff` 零偏离 | `diff` |
| A5 | 一次参数扫描（失真率五值乘十种子）产出曲线 | `sweep` |

### 4.3 风险、后置代价与未达标处理

最大的风险是决断的「感觉不对」没有客观标准，迭代时间不可控。对策是性质断言先行：断言通过即算达标，「打得好不好」留给人工对局，M3 不承担这一项。

第二个风险是行为失衡。某方必胜会让批量结果单一，对策是先调参数边界，不改代码；陡峭区记入 M4 待办。

后置代价：认知与决策会反过来暴露档案结构、参数边界与命令翻译的不足。推迟到接界面时集中出现，修改会同时牵动契约、翻译与界面。

未达标处理：A3 不过即冻结 M4。决策不可解释，人类入口接上也没有意义。

## 5. M4 可交付

**目标**：人类入口与界面接入，两种玩法均可完整走完一局，参数可扫描调校。

**前置**：M3 验收通过。

### 5.1 任务分解

#### 5.1.1 人类命令入口（1 周）

- 友方决断相位接受人类输入覆盖自动决断，输入格式与自动决断输出完全一致。
- `play` 提供命令行对局。
- Flutter 端从直接调内部方法改为只调引擎公开入口，清掉界面与引擎同居的最后残留。
- 上帝视角玩法作为第二个入口接入：绕过指挥部直达引擎，两种玩法共用同一套结算。

#### 5.1.2 开发仪表盘（1.5 周）

| 仪表 | 数据来源 | 铁律 |
|------|----------|------|
| 信念轨迹图 | 事件卷与信念卷 | 只读档案，不做活体查询 |
| 通信时间线 | 情报卷 | 同上 |
| 决策追踪器 | 决策卷 | 同上 |
| 战损分布图 | 批量结果 | 同上 |

先在命令行以文本与简图交付，Flutter 可视化视余力决定。

#### 5.1.3 参数扫描调参（1.5 周）

- 扩展 `sweep`：失真率、谨慎度权重、信念重算周期。
- 结果存档，跨版本对比，漂移方向可见。
- 建立每周重演金标准对局并重扫参数的节奏。

#### 5.1.4 三线后果（1 周）

- 军事、消耗、政治三线填充 M2 预留的后果槽位。
- 三线数值进参数表，想定文件同步更新。

#### 5.1.5 补给深化（1 周）

- 从连通性判断升级为完整补给模型。
- 补给参数的敏感性纳入常规扫描。

#### 5.1.6 文档同步（0.5 周）

- 现状文档改为按里程碑记述。
- 验收场景与新增场景对照落档。
- 架构说明书升版，吸收两种玩法、六角格归属与后果槽位。

### 5.2 验收标准

| 编号 | 标准 | 验证方式 |
|------|------|----------|
| A1 | 人经命令行打完整一局，档案齐备 | 人工加 `validate` |
| A2 | Flutter 端两种玩法均可运行 | 人工验收 |
| A3 | 四张图读档案出图，开发期每周被使用 | 使用记录 |
| A4 | 一轮扫描存档，与上周曲线可比 | `sweep` 结果 |
| A5 | 三线后果在战报中可见 | 战报审查 |

### 5.3 风险、后置代价与未达标处理

最大的风险是范围蔓延，M4 最容易被反复打磨。对策是 A1 至 A5 通过即封版，剩余项进待办，不阻塞关闭。

第二个风险是仪表盘打磨失控。对策是文本形态先验收，可视化算加分项。

后置代价：界面推到最后，命令通道表达不了的交互会集中暴露；此时补要同时改契约、翻译与界面。

未达标处理：A1 不过即不封版，先补人类入口的档案完整性。

## 6. 未决事项

以下四项尚未裁决，裁决前正文按现有实现与串行顺序书写。

| 事项 | 待选项 | 影响 |
|------|--------|------|
| 首个正式想定 | 睢杞、帝丘店 | M1 的输入定名，M4 的验收素材 |
| 指挥层级档数 | 两档、三档 | M3 的命令展开层数，M4 的界面范围 |
| M2 与 M3 的关系 | 串行、并行 | 档案结构的冻结时点 |
| 大模型接入 | M4 内、交付后 | 验收是否覆盖文字层回归 |

裁决后只改受影响的里程碑，不改四段骨架。

## 7. 跨阶段纪律

- 确定性测试常青：同种子双跑零偏离在每个里程碑结束与每次引擎改动后必跑，不通过即回滚。
- 档案只增不改：不引入改写档案的接口，记录的写入点从 M1 锁死。
- 数值不进代码：新增数值一律进参数表并记指纹，lint 查裸数值。
- 文档随代码走：每个里程碑关闭时更新现状文档与受影响的规范。
- 金标准对局滚动维护：M2 起每次录制金标准局后编号存档，M3 与 M4 的机制改动均重演对比。

```

├─ 拆包 engine/，迁 combat、game、battlefield、阶段枚举

└─ 验收：同种子双跑零偏离

M2 可复盘（3–4 周）     消除 G2
├─ 战斗与补给模块化 + 十相位 + 关卡翻译 + 情报卷
├─ 想定 v1（援军波次、胜负条件、后果槽位）+ 命令行入口
└─ 验收：五卷齐备，注错三分钟定位

M3 可对弈（6–8 周）     消除 G3
├─ 指挥部包 + 类型隔离 + 过滤、延迟、失真、研判、决断、参谋

├─ 人类入口 + 界面接回公开入口 + 上帝视角玩法 + 仪表盘
```
